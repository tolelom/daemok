# 개요

> 확정된 결정만 담는다. 검토 중인 설계는 번호가 붙은 다른 문서에 있다.

## 문제

- 설계가 여러 문서로 흩어져 진행되고, 전체 모습을 한곳에서 볼 수 없다.
- 같은 사실이 여러 문서에 따로 적히고, 한쪽만 고쳐지면서 어긋난다.
- 구조를 바꾼 뒤에도 다른 문서는 옛 이름을 참조한다.
- 자연어 설계는 AI가 코드로 옮기면서 해석이 갈린다.
- 구현 중에 설계가 바뀐다. 원인은 AI의 이탈, 구현하다 코드만 고치고 문서를 두는 것, 요구사항의 외부 변경이다.

## 우선순위

대상은 먼저 tolchain·tolelog 같은 자기 프로젝트다. 다른 사람이 쓰는 도구로 넓히는 것은 그 뒤이고, 아래 순서는 이를 따른다. 형식과 구조는 두 번째 구체 사례가 생길 때 넓힌다.

| 순위 | 목표 |
|---|---|
| 1 | 흩어진 설계를 한곳에서 보고 관리한다 |
| 2 | 설계를 바로 코드로 옮긴다 |
| 3 | 기존 프로젝트에도 도입할 수 있다 |

## 원칙

1. 모든 사실은 ID가 붙은 한 곳에서만 정의하고, 다른 곳은 참조만 한다. 깨진 참조는 도구가 잡는다.
2. 방향은 설계에서 코드로 하나다. 코드에서 설계를 뽑는 기능은 기존 프로젝트를 처음 가져올 때만 쓴다.
3. 모든 설계 요소는 코드로 나타난다. 코드가 되지 않는 설계는 문서일 뿐이다.
4. 사람이나 AI가 쓰는 것은 함수 본문뿐이다. 생성 파일(첫 줄에 생성 헤더가 있는 파일)은 손으로 고치지 않는다.
5. 검증은 문서 비교가 아니라 컴파일러, 의존 검사, 생성된 테스트가 한다.
6. 설계 변경은 막지 않는다. 설계를 고치고 다시 생성하는 비용을 코드만 고치는 비용보다 낮춘다.

## 계층

| 층 | 내용 | Go 생성물 |
|---|---|---|
| R | 요구사항. 본문은 자연어, ID로 참조 | 없음. 설계 요소가 `satisfies`로 연결 |
| L0 | 시스템, 액터, 외부 인터페이스 | 외부 경계 인터페이스 |
| L1 | 실행 단위 | `cmd/<name>/main.go`와 조립 코드 |
| L2 | 모듈, tier, 의존 규칙 | 패키지 디렉토리, 허용되지 않은 import 검사 |
| L3 | 타입, enum, 상수, 에러, 계약(interface, 핸들러 함수 타입) | struct, interface, const, sentinel error, 등록 코드 |
| L4 | 함수 계약(시그니처, 에러, 케이스 표) | 시그니처 확인 코드, 테이블 테스트 |

상위 계층을 확정한 뒤 다음 계층으로 내려간다. AI는 한 번에 한 계층만 제안한다.

## 구조

- 자체 모델과 Go로 만든 CLI 하나. 파일 감시, 검증, 코드 생성, import 검사, 지도가 그릴 상태의 JSON 제공, MCP 서버(`daemok mcp`, 읽기 전용 도구)를 한 바이너리가 맡는다. 명령 목록은 [README](../../README.md)에 있다.
- 화면은 `serve`가 embed한 웹 페이지이고 이 JSON을 그린다. 에디터 패널이나 데스크톱 창은 이 페이지를 감싸는 방식으로만 더한다. 화면에서 하는 L2 편집(모듈의 tier, `depends_on`, 모듈 추가)은 설계 파일의 해당 줄만 고치고, 승인은 커밋이다.
- 설계의 기준은 git HEAD의 설계 파일이다. 지도는 작업 중인 파일과 HEAD의 차이를 표시하고, 승인은 커밋이다.
- 외부 의존성 없음. Go 표준 라이브러리만 쓴다.
- 설계 파일은 YAML의 엄격한 부분집합이다. 지원하지 않는 문법은 줄 번호와 함께 에러를 낸다. 전용 언어는 YAML이 실제 병목이 될 때 따로 검토한다.
- API 계약은 새로 정의하지 않고 OpenAPI 파일을 경로로 참조한다.
- 1차 대상 언어는 Go다. 포맷의 언어 중립성은 이후 UE5 C++ 프로젝트로 확인한다.

## 다른 언어

설계 모델에서 언어별 요소는 `go:` 같은 이름 규칙에만 있다. 언어 하나를 지원하려면 모델에서 소스 텍스트를 만드는 생성기와 모듈 간 의존을 읽는 import 스캐너가 필요하다.

| 언어 | 의존 선언 |
|---|---|
| C, C++ | `#include` |
| UE5 C++ | `*.Build.cs`의 `PublicDependencyModuleNames`, `PrivateDependencyModuleNames` |
| TypeScript | `import ... from`, `export ... from`, `import()` |
| Python | `import`, `from ... import` |

타입이나 시그니처가 설계와 맞는지는 파서를 만들어 확인하지 않는다. 생성 코드 안의 확인 구문을 대상 언어의 컴파일러가 검사한다. Go는 `var _ Handler = f`, C++은 `static_assert`, TypeScript는 `satisfies`를 쓴다.

## 기존 도구와의 차이

| 도구 | 하는 일 | 차이 |
|---|---|---|
| OpenAPI, TypeSpec, Smithy, Protobuf | API 계약에서 코드 생성 | API 경계만 다룬다 |
| MDA, UML 라운드트립 | 모델에서 코드 생성 | 모델이 코드만큼 상세해야 했다. daemok은 뼈대까지만 모델로 정하고 본문은 사람이나 AI가 채운다 |
| Spec Kit, Kiro | 마크다운 명세로 AI 구현 | 명세가 자연어라 해석 여지가 남는다 |
| [Ossature](https://github.com/ossature/ossature) | 섹션 규약이 있는 마크다운 스펙·아키텍처와 고정 문법의 검증 케이스에서 LLM이 코드를 빌드 | 요구사항 ID가 없다. 결정적으로 생성하는 것은 테스트 하네스뿐이고 계약 준수는 LLM 리뷰가 판정한다. import 규칙 검사, 시각화, 기존 코드 도입이 없다 |
| Structurizr, LikeC4 | 텍스트를 다이어그램으로 | 코드 생성과 검증이 없다 |
| go-arch-lint, arch-go, depguard | import 규칙 검사 | 검사만 하고 설계 모델이 없다 |
