# daemok coverage

> [tolchain 슬라이스](../design/02-slice-tolchain.md)의 "설계 노드 대응 비율"을 손으로 세던 것을 명령으로 만듭니다. 이 비율은 형식을 넓힐지 정하는 근거입니다.

## 세는 규칙

| 항목 | 규칙 |
|---|---|
| 패키지 | 코드 루트 아래 Go 파일이 있는 디렉토리. 파일 선택과 건너뛰는 디렉토리는 `internal/gosrc`(codescan과 같음) |
| 최상위 선언 | 패키지의 type, const, var, 메서드가 아닌 func 이름. `_`, `init`, `main` 제외. `_test.go` 제외 |
| 설계 대응 | 최상위 선언 중 설계가 그 패키지에 만드는 이름. 모든 L3·L4 노드를 `gen: true`로 보고 생성한 Go 코드의 최상위 선언 이름, 등록 파일이 가리키는 핸들러 함수 이름, 일반 함수의 Go 이름 |
| 함수 제외 비율 | 최상위 선언과 설계 대응에서 메서드가 아닌 함수를 뺀 비율. 설계는 에러 계약이 있는 함수만 두므로 함수가 합계 비율을 낮추는 정도를 따로 봅니다 |
| unexported | 뺀 비율을 두지 않습니다. 저장 키 접두사, keystore 반복 횟수, 페이지 크기 상한처럼 시스템 경계에서 보이는 값이 unexported로 있고, 설계 대응에도 핸들러와 생성 보조 선언(`daemokUndo` 등) 같은 unexported 이름이 있습니다 |

`gen: false` 노드도 생성했다고 보고 이름을 얻으므로, 손으로 쓴 선언이 설계 노드와 이름이 같으면 대응으로 셉니다.

## 명령

`daemok coverage [--design DIR] [--root DIR]`

패키지별 최상위 선언 수, 설계 대응 수, 비율, 함수 제외 비율과 합계를 표로 출력하고, 표 아래에 함수를 뺀 선언·대응 수와 함수의 선언·대응 수를 한 줄로 적습니다. 설계를 읽지 못하거나 설계 검사 오류가 있으면 2, 그 밖에는 0입니다. 설계 대응 이름을 얻으려고 코드를 생성하는데, 생성은 검사를 통과한 모델을 전제로 하기 때문입니다.

## 테스트

| 대상 | 확인 |
|---|---|
| 세기 | 임시 모듈에서 `gen: false` enum의 타입·상수, 손으로 쓴 다른 선언, 메서드, `init`, `_test.go`가 규칙대로 세어지는지 |
| 핸들러 | 그룹 멤버의 `handle<Value>` 함수가 대응으로 세어지는지 |
| 실제 | tolchain `feat/daemok`의 `a97cbb0`에서 슬라이스 문서의 합계(355, 124)와 비교 |
